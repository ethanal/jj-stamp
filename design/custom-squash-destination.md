# Custom squash destination: three interactive concepts

Design only. No application/API or squash behavior changed. Open
`design/custom-squash-destination.html` in a browser, or use the standalone
`.planka-artifacts/index.html` preview generated by the checks below.

## Shared visual model

- Preserve the existing **monospace graph with normal line height**: literal
  graph prefix, change ID, bookmarks, and description all share one line. No
  commit cards, extra vertical padding, wrapped titles, or invented connector
  lines. Long rows scroll horizontally, as in the current log.
- Default to the reviewed change's **immediate parent**, not the next visible log
  row. The example starts at `vqkqszmu → pqxvqmoo`.
- Keep the existing blue review highlight. Give the destination a separate amber
  inset edge, inline `[target]` label, and a compact summary above the log.
  Labels—not color alone—distinguish the two roles. All inline controls and
  annotations inherit the graph's font size and line height.
- Repeat the destination in the existing file-sidebar footer and alongside the
  selected-line squash action, including when the log isn't visible.
- Choosing a destination leaves the source diff and selected lines unchanged;
  it does **not** immediately squash. Reset returns to the immediate parent.
- A custom destination outside the log filter gets a compact pinned summary;
  don't silently change the filter or substitute a visible commit.

## A — Direct row action (recommended)

Hover or keyboard-focus an eligible row to reveal **[↓]** (Set destination). The
change ID retains its separate review-navigation role. One candidate's action
is exposed by default to make the feature discoverable; touch/narrow layouts
show all actions. **Pick in log** also provides an explicit, keyboard-accessible
entry into the full-row picker used in B. The action stays inline after the
description without increasing the line height.

This is the shortest path when the desired commit is already visible, and keeps
the log's navigation model intact. Its tradeoff is the extra inline action.

## B — Pick in the log

**Change…** enters an explicit destination-selection mode with a banner and
Cancel button. Eligible rows become clickable across their existing width,
without changing their normal line height; IDs choose destinations rather than
navigate until the mode ends. Source and immutable rows cannot be chosen.
Escape/Cancel leaves the current destination unchanged and returns focus to the
entry control.

This has a cleaner resting log and larger targets, but introduces a temporary
mode. The banner is essential to avoid confusing destination selection with
review navigation.

## C — Compact search picker

**Change…** opens a picker next to the destination summary. Search fixture titles
or change IDs; choose with the mouse or Up/Down and Enter. Source and immutable
results explain their unavailable state. No matches leaves the target unchanged.
Escape, Close, or clicking outside cancels and returns focus. Results include one
target outside the visible log, shown explicitly after selection.

This scales to older/offscreen destinations at the cost of an extra interaction
and a second list. It could complement A later instead of replacing it.

## Illustrative guardrails / implementation questions

The example-state selector demonstrates the parent default, custom ancestor,
queued-work lock, and target outside the filter. These are fixtures, not live jj
reads. Squash only reports what would happen; review navigation, Go to, and
Settings are intentionally not simulated.

For implementation after design approval:

- Scope an override to the reviewed source. Switching sources should start with
  the new source's immediate-parent default, rather than inherit a hidden target.
- Pin each queued batch's source and destination, and disable target changes
  until the queue drains. The mockup's queue is illustrative and never runs.
- Resolve by full change identity, then revalidate/pin commit IDs at mutation
  time. Never treat a visual row or cached search result as write authority.
- If the source has multiple parents or its parent is immutable, explain why
  there is no safe default; don't silently use the next log row. The mockup only
  illustrates a single mutable-parent source and immutable candidate exclusion.
- Decide allowed relationships (older ancestors only, or other branches too),
  conflict handling, descriptions, undo, and stale/missing target recovery before
  implementing custom squash. Fixtures illustrate older ancestors only, not a
  promise that every mutable commit is a valid destination.
- The current backend and native selection engine are immediate-parent-only.
  Custom destinations require backend/queue safety work, not just a UI parameter.

## Checks and captures

From the repository root, with npm dependencies and Playwright Chromium installed:

```sh
node design/custom-squash-destination.e2e.mjs
```

The check generates a standalone HTML/font bundle and five PNGs in the ignored
`.planka-artifacts/` directory. It checks all three selection paths, source and
line-selection preservation, default/reset, cancellation and focus return,
keyboard controls, unavailable candidates, search/no results, queued-work locks,
off-filter destinations, narrow layout, and standalone preview interaction.
It also checks normal line height, contiguous unpadded rows, aligned monospace
graph columns, inline descriptions/controls, and horizontal scrolling at narrow
widths; it rejects uncaught page errors and HTTP/API requests.

The mockup uses the existing local Source Code Pro font and dark palette, without
CDNs. No production builds, backend tests, or real-jj mutations are needed to
exercise these design files.
