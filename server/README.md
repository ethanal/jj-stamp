# Review backend

The CLI constructs `ReviewService({ repoPath, revision })` and passes it to `createApi(service)`. The repository path is explicit; all app operation bookkeeping is held in memory only. There is no default singleton, demo repository, environment-based repository switch, or reset API. `revision` defaults to `@` and is resolved once at startup to one visible, non-divergent full change ID.

`server/http.ts` serves the bundled UI and router on `127.0.0.1`. It validates Host and Origin before any route, rejects cross-site requests, and requires JSON plus `X-Fold-Request: 1` for mutations. Browser launch and graceful shutdown live in `cli.ts`.

Unversioned UI files (especially `/` and `/index.html`) use `Cache-Control: no-store`, without ETag or Last-Modified validators. Nix normalizes file timestamps, and different entry pages can have identical sizes; stat-based validators could otherwise return a false 304 and leave the browser requesting obsolete hashed bundles after an upgrade. Content-hashed `/assets/` files retain conditional caching. Missing static files return uncached plain-text 404s, never an HTML fallback.

## Native diff editor (experimental branch)

Only Node.js and `jj` are required. Pinned Git diffs are parsed locally and assigned deterministic hunk IDs (short hashes of exact path/header/rows, with collision suffixes). No third-party hunk listing, patch generation, GNU `patch`, or fuzzy matching is involved.

`selection.ts` consumes a selected file's pinned base/source **bytes**, complete parsed diff, and one-based selected patch-body rows. It validates every hunk, coordinate, unchanged gap and tail by reconstructing the entire source exactly before deriving the selected result. Only lossless UTF-8, regular non-executable text with final newlines is supported initially. New/deleted files distinguish absence from an empty file. Preview text is produced by the same function for display; it is never parsed to apply the selection.

Preparation reads both pinned file sides through `jj file show --ignore-working-copy` (skipping absent sides), then repeats the existing live version/eligibility checks after the conflict baseline. Execution invokes `jj squash --from <full-source> --into <full-target> --tool jj-stamp --use-destination-message --keep-emptied` with literal filesets restricting jj's scratch trees to the selected files. The callback pins directory invocation mode, overriding same-named repository tool settings; `ui.diff-instructions=false` keeps those inventories unambiguous.

`diff-editor.ts` creates a per-invocation 0700 temporary directory and 0600 JSON manifest containing canonical base64 base/source/result bytes. The configured Node callback (`diff-editor-cli.ts` in source, bundled `dist/diff-editor.cjs` when installed) validates the entire left/base and right/source inventories **before any write**. It rejects mismatches, extra/missing files, traversal, aliased roots, overlapping/workspace roots, symlinks and hard-linked/nonregular inputs. It replaces only the right-side files with the precomputed selected result; jj owns the subsequent history rewrite. Temporary outputs are written with exclusive creation and renamed into place. This is not a filesystem transaction against malicious concurrent local processes.

The manifest directory is removed on success or failure, never reused, and is not durable recovery state. An uncatchable process/VM crash can leave private temporary bytes in the system temp directory. Error diagnostics include the exact executed command and working directory, but explicitly warn that the deleted manifest makes that command **not replayable**. No failure, cleanup, refresh or restart automatically retries a mutation.

The Nix launcher pins `JJ_STAMP_JJ` to its absolute executable path for reads, mutations and diagnostics. The callback uses the current process's absolute Node executable; its sibling bundle is installed alongside the CLI. Without that override, ordinary PATH lookup is retained for jj. No Rust or patch runtime is bundled.

## Revision identity

Reads use `change_id("<full-id>")`, not a moving `@`, bookmark, or mutable commit hash. Source commits are re-resolved live to follow rewrites. Every revision includes `author` (the author name) and `changeIdPrefix` (jj's shortest distinguishing prefix), fetched in the existing metadata queries for state, selection and graph reads. A selected change with no visible revision returns `SOURCE_UNAVAILABLE` with its full change ID and a missing/possibly abandoned diagnosis; multiple visible revisions are reported separately as divergent. It never silently redirects to the working copy. A healthy `@` does not establish that the pinned source is healthy: moving the workspace leaves the selection unchanged, and jj can automatically abandon an empty undescribed working copy when leaving it. Conflicts on other branches or resolved ancestors do not make the source unavailable. Startup rejects an empty, ambiguous, hidden, or divergent selection with `INVALID_REVISION`.

Explicit `POST /revision` is the only way a running session changes its source. It is serialized and version-checked, accepts immutable and conflicted changes for read-only viewing, preserves the previous source on validation failure, and invalidates old preview tokens on success. The process-local history state remains in place. A pending in-memory guard blocks revision switching as well as mutations. State and file reads remain available for immutable or conflicted sources. The graph also remains readable if the prior source becomes missing or divergent. To recover explicitly, fetch the graph and submit its current `version` with the chosen change ID to `POST /revision`; the old unavailable-source identity and availability are versioned and revalidated along with the candidate. A stale token, missing/divergent candidate, or intervening operation fails without changing the selected source. No graph read automatically selects `@` or clears the pending guard.

Every squash-eligible state exposes the exact single **mutable immediate parent**, otherwise `parent: null` and `squashUnavailable`. Immutable and conflicted sources return their diffs with empty `targets` and a read-only reason; both direct squash and legacy preview/squash reject them. Eligibility remains part of the versioned view, so conflict or mutability changes during reads or preparation still invalidate stale requests. Merges and immutable parents cannot squash; an older ancestor is never substituted. A merge can be selected and displays its reason in the UI.

## API

- `GET /state`: selected source, mutable ancestors (`targets`, for the legacy preview API), exact `parent`, optional `squashUnavailable`, Git patches, native hunk IDs and one-based patch-body rows, operation/version, and `canUndo`.
- `POST /revision {version,changeId}`: select one visible, non-divergent change, including immutable or conflicted changes for viewing; returns `{state}`. The browser supplies a full change ID from the graph. Revision expressions are accepted only as the CLI's initial positional argument, not through this endpoint.
- `GET /graph`: `{version,rows}`. The browser uses this read-only revision-graph endpoint; it skips rendering unused compatibility text and avoids the logging-shaped `/log` path that browser filters may block. Legacy `GET /log` returns `{version,output,rows}` and `GET /log?format=rows` remains an alias for the rows-only response. `output` uses the configured text template with the explicit review revset `visible() & (trunk() | (tracked_remote_bookmarks() & ~::trunk()) | (mutable() & mine())::)`. `rows` uses the actual jj graph renderer and a machine-readable template. Each row has `graph` and optional `revision`, `mutable`, `isWorkingCopy`, `isEmpty` (jj’s `empty` predicate). Connector rows contain only `graph`. The structured view uses exactly the same revset, with no arbitrary 100-entry cap or extra unions for the selected change and working copy. Those changes appear only when they match the filter; filtering them out does not change the selected source. Its `version` is also available when `/state` reports an unavailable source, so the browser can explicitly choose a valid replacement. The app supplies this revset directly instead of fetching the default `revsets.log`. A random delimiter separates graph prefixes from JSON metadata. Descriptions are never interpreted as markup.
- `POST /editor {version,path,line}`: open the actual absolute workspace file at a positive, one-based line in an existing Neovim session at `127.0.0.1:4242`; returns `{ok:true}`. Requires the same JSON and `X-Fold-Request: 1` protection as other POST endpoints. Validates the current selected source/version and exact diff path, rejects deleted, missing, nonregular and symlinked files (including symlinked directories), and serializes with all other requests. It neither snapshots jj edits nor rewrites history. Historical selections still open current workspace bytes, not historical contents; lines past the end of the loaded editor buffer are clamped to its last line.
- `POST /commit {commitId}`: immutable **display-only** content `{repo:{name,path},commitId,baseCommitId:string|null,files:ReviewFile[]}`. Requires a full lowercase hexadecimal commit ID (exactly 40 or 64 characters), never a short ID, change ID or revset. Metadata, diff and both file-side revision arguments use `commit_id("<full-id>")`, never bare hexadecimal symbols that a same-named bookmark could shadow. The exact identity is also checked against jj's metadata result, including for hidden commits after rewrites. Returns the same parsed patches/hunk IDs as state. Merge commits fail with `422 UNSUPPORTED_DIFF`; the root commit has `baseCommitId:null`. No selection, initialization of the selected source, workspace snapshot, live-version check or mutation authorization occurs.
- `POST /commit-file {commitId,path}`: immutable immediate-parent/source `{oldFile,newFile}` display contents. Each existing side is `{name,contents}`; an added/deleted side is null. Only exact supported changed paths from that commit's parsed diff are accepted, with a single-parent context and literal root-relative filesets. Traversal, unsupported files and paths outside the diff fail closed. Like `/commit`, this route does not return a version or authorize any mutation. Both routes retain the existing same-origin loopback, JSON and `X-Fold-Request: 1` POST protections and `Cache-Control: no-store`.
- `POST /file {version,path}`: full pinned immediate-parent/source file contents for a supported file in the current diff. New/deleted sides are null. Invalid paths, unsupported formats, merge context, and stale versions are rejected. Reads use literal root-relative filesets after `--`.
- `POST /squash-lines {version,selections:[{id,lines}]}`: squash the exact selected changed rows from the selected change into its single mutable immediate parent. No target override or extra properties are accepted. Constructs and verifies exact pinned selected file bytes, rechecks live state in the same serialized task, and sets an in-memory pending guard before execution. Returns `{state,output,warning?}`.
- `POST /undo {version}`: revert only the last exactly attributed app squash via `jj op revert <operation>`, while the selected-source state and repository operation still match. Undo is available only in the process that performed the squash, not after restart.
- Legacy `POST /preview {version,target,selections:[{id,lines}]}` and `POST /squash {token}` remain for internal compatibility/tests. They are not used by the UI. Whole-hunk selections contain only changed rows; tokens are one-shot, expire after ten minutes, and do not survive restart.

Unknown routes, including `/reset`, return 404. Errors are JSON `{error,code,output?}`. Invalid inputs use 400; stale, conflict, unavailable-source and recovery conditions use 409; unsupported/unsafe previews use 422; tool failures use 500.

## Workspace editor

Install `nvim` on the backend's PATH and start your editor with `nvim --listen 127.0.0.1:4242` (or use Neovim's `serverstart('127.0.0.1:4242')` in an existing session). The UI's `e` shortcut opens the cursor's file/line there. The backend runs `nvim --server 127.0.0.1:4242 --remote-expr` with an argument array; it never launches a replacement editor or falls back to opening a terminal. Missing executables, unavailable sessions and rejected editor commands return `503 EDITOR_UNAVAILABLE` with setup guidance. File eligibility failures return `422 EDITOR_FILE_UNAVAILABLE`.

The expression passes a literal filename to `bufadd`/`bufload` and positions the cursor with the Neovim API. Filenames are not Ex commands, shell text, key sequences or wildcard expressions. Existing loaded buffers retain their unsaved contents. Normal user-configured editor autocommands still apply. Filesystem containment is checked again immediately before dispatch, but external filesystem changes can still race the editor opening a path; do not concurrently replace workspace files or directories with symlinks.

## Safety

All existing mutable-state requests, including reads which may snapshot jj, share one serial queue (at most 64 accepted active/waiting tasks; overload returns `503 BUSY`). Immutable `/commit` and `/commit-file` display requests use an independent bounded lane: two active tasks and at most sixteen waiting tasks, with `503 BUSY` on overload. They never wait on or enter the serial queue, and never alter session history, preview tokens, selection, initialization or the demand diff cache. All their jj subprocesses use `--ignore-working-copy`, including root/metadata lookup and both file sides. They share an isolated display-only descriptor LRU (ten commits, at most 8 MiB estimated retained bytes) with in-flight deduplication by exact commit ID; caller-side speculation cannot populate or evict the existing demand cache. Warm file reads launch only the existing file-side `show` commands, without repeating root, metadata, or diff reads. Public commit results are cloned so callers cannot change cached paths or parent identities. Errors and unsupported interpretations are not retained; oversized descriptors bypass the cache without evicting useful entries. Response and retention bounds are checked before insertion. No full file bytes are cached. Cache/in-flight access happens only within the bounded read lane, and shared subprocess timing belongs to the initiating task. These reads may overlap mutations but remain pinned to exact immutable commit/parent IDs. Missing/pruned commits fail without changing mutation state. The root lookup, metadata, raw diff and each file-side capture are bounded to 64 KiB, 64 KiB, 2 MiB and 4 MiB respectively; serialized responses are capped at 16 MiB. Oversized reads return `413 CONTENT_TOO_LARGE`. Only these opt-in read subprocesses may be killed for exceeding their output budget; mutation runners retain their existing behavior and process budgets. For diff reads and mutations, one metadata query snapshots the workspace and reads the source, conflicts, parent and mutability; a second query revalidates them after the requested work, followed by an operation-head check. Revision selection batches the old and candidate views into the same two queries. Graph and editor reads use metadata queries with `--ignore-working-copy` (including cold initialization); graph reads never load diffs or prepare selected file contents, and render with `--at-operation` at the captured operation. Showing the log never snapshots the working copy: it reflects recorded repository history, not unsnapshotted edits. External recorded operations and relevant eligibility/configuration changes during graph reads still invalidate the response. Execution uses full pinned commit IDs and argument arrays, with `--use-destination-message --keep-emptied`. There is no shell interpolation, interactive editor, mutation timeout, or automatic retry.

On POSIX, child tools run in separate process groups with referenced pipes. Terminal Ctrl-C therefore stops the CLI from accepting requests without interrupting a jj history rewrite. Shutdown waits for HTTP requests, the serial service queue and all accepted immutable display reads (including queued/failed reads and their children) to drain; child processes are not abandoned.

Startup resolves the requested expression and checks `hidden`/`divergent` in one jj query, rather than spawning another process to resolve its visibility. The initial pinned diff/cache read overlaps the non-snapshot operation query; both finish (including on failure) before the queue can advance. Final metadata revalidation and the operation-head check remain sequential. A cold state needs seven service-launched subprocesses; local hunk IDs require no extra listing process. Live eligibility and safety checks remain uncached.

Squash and preview preparation capture pinned inputs privately; they do not publish state or authorize a write until selected-file construction and live metadata plus operation revalidation complete. Squash performs its final check **after** the conflict baseline, immediately before installing the pending guard and executing once. File/editor final checks also read metadata and operation only. A warm direct squash of one existing file with a nonempty resulting diff uses 15 service-launched subprocesses; a legacy preview uses four validation processes plus one `file show` per existing selected side. The nested callback is included in the mutation, not counted separately.

Metadata queries restrict their conflict-membership lookup to the same source/parent/ancestor union they render. This is set-equivalent for every returned row, including custom `conflicts()` aliases, but avoids searching all visible history just to classify a few revisions. Both initial and final validation use this bounded query. Graphs still perform both live recorded-metadata checks around their pinned render; no graph cache or unvalidated version reuse was introduced. Configured shortest-prefix semantics are unchanged.

Global pre/post squash conflict checks return only full change IDs, not descriptions, authors or shortest prefixes, and do not snapshot the workspace themselves. The following final metadata/operation checks cover intervening edits/history changes. These sets still span the repository: restricting them to a descendant cone would change behavior for some configured `conflicts()` aliases. Malformed IDs fail closed; a post-attribution warning-read failure reports a completed squash and disables undo without leaving a false pending guard.

Source diffs and locally identified hunks use a bounded 16-entry cache keyed by repository and immutable commit ID. A cache miss reads one pinned Git diff, regardless of file count. Unsupported files are quarantined without hiding other files. Returned state is cloned and unsupported interpretations are not cached. Operation tokens, snapshots, mutability/configuration, graph output and full states are never cached. Pinned file contents are re-read and validated during every preview/mutation preparation.

Binary/combined diffs, renames/copies, mode changes, missing final newlines, ambiguous/header-like rows, and whitespace/quoted paths fail closed. Conflicts elsewhere in the repository do not block review or squash. The selected source must be mutable and conflict-free to squash, but not to view. Its mutable immediate parent may contain conflicts: selected resolution rows can be squashed incrementally while unselected conflicts remain. Older conflicted ancestors remain excluded from legacy squash targets. Pinned conflict-marker bytes receive the same full-diff reconstruction and scratch-tree validation as ordinary text; jj interprets the selected result when rewriting history. Post-squash warnings report newly conflicted changes, not pre-existing conflicts.

An in-memory pending guard is set before execution. Successful attribution requires exactly one operation descended from the validated operation, the expected destination description, and tool attributes naming the pinned source/destination. A zero-exit squash that passes this live attribution check clears its pending guard **before** loading or validating its updated view. Subsequent snapshots or rendering failures disable undo and return `HISTORY_CHANGED`, explicitly reporting that the squash completed; they do not leave a false pending-mutation guard or incorrectly claim nothing was squashed. Exact undo is recorded in memory only after the post-success state validates at that same attributed operation.

History changes before attribution, unreadable operation metadata, and nonzero tool exits with changed/unknown history remain ambiguous and block further mutations in the current process. There is no scanning backward through later snapshots to infer success, no replay, and no rollback. Reads and browser refreshes never clear an ambiguous guard or retry an operation. Restarting the service discards all app bookkeeping, including pending guards, undo and preview tokens; it does not inspect, change, or repair repository history.

External jj processes and file edits cannot be locked by this in-process queue. **This is not an atomic cross-process transaction.** An external edit can race final validation and tool execution; detection may occur after squash. Avoid concurrent edits/history operations and run only one app process per repository. Multiple browser tabs share the process's selected change; do not mutate concurrently across tabs.

## In-memory operation state

The backend stores no durable app state on disk (see the short-lived native callback manifest above). There is no `dataDir` option, app state directory, operation journal, startup journal read, or recovery-file migration. Neither `$XDG_STATE_HOME/jj-stamp` nor `~/.local/state/jj-stamp` is read or written. Existing `operations-*.json` files from older versions are ignored and left untouched; they are never deleted, interpreted as a guard, or used to restore undo.

Squashes and undo still make their normal changes to jj's repository and operation history. Those jj changes survive restart; app bookkeeping does not. A fresh service begins with no undo, pending guard or preview tokens, even if an older process stopped during an operation. This intentionally provides no durable crash-recovery guard: inspect `jj op log --no-pager` after an interrupted or ambiguous operation before submitting new work. Never blindly repeat the prior squash or use `jj op restore` as an automatic rollback.

For `PARTIAL_FAILURE` or `RECOVERY_REQUIRED`, and for `HISTORY_CHANGED` errors that contain a `pending` field, inspect the operation log before restarting. Errors include `pending` and `recoveryAction` details, with the same essential information in the human-readable message: operation kind, full pre-operation ID, and source/target commits and change IDs. Restarting forgets the guard; it does not reconcile the failure or retry the operation. There is no reset or automatic recovery API.

A `HISTORY_CHANGED` response explicitly saying **the squash completed and was attributed** is different: its `completedOperation` identifies the confirmed squash and no pending guard remains. Inspect history and refresh; automatic undo is unavailable, and any subsequent squash needs a fresh explicit review. Errors stop the browser's queue rather than replaying queued selections.

A snapshot following a squash in `jj op log` alone cannot determine which case occurred: it may have appeared before attribution or during post-success rendering. Diagnosis requires comparing the failed request's `beforeOperation` and source/target commits with the full operation chain and the initial failure, not just the most recent operation.

Initialization failures are memoized. Retrying cannot reinterpret the original `@` or another moving revision expression. Repair the underlying problem and restart the process.

## Timing diagnostics

`jj-stamp --trace` opts into one completed-operation JSON line on stderr, prefixed `[jj-stamp timing]`. The initial startup state read is included. Embedders can supply `ServiceOptions.onTiming(record)` instead; no tracing is enabled by default. This adds no subprocesses, retries, or safety-check changes.

Each record has a service-local increasing `id`, stable operation `name` (`state`, `revision`, `graph`, `log`, `editor`, `file`, `commit`, `commit-file`, `squash-lines`, `preview`, `squash`, or `undo`), `queueMs`, `durationMs`, `ok`, and `subprocesses`. Durations use a monotonic clock in milliseconds. `queueMs` measures waiting for the operation’s serial or display lane; `durationMs` excludes that wait and observer execution. Each subprocess has an allowlisted command `name`, `startMs` relative to task start, `durationMs`, and `ok`, in invocation order. Log labels distinguish metadata, graph and conflict queries, and whether they allow a working-copy snapshot (`snapshot`), ignore it (`recorded`), or use a captured operation (`pinned`). Overlapping subprocess durations must not be added to infer task duration. A handled subprocess failure can appear in an otherwise successful operation.

Only service-launched jj and workspace-editor calls are measured (including injected runners); the nested native diff-editor callback and the CLI's preflight version probes are not separately instrumented. Traces contain no arguments, cwd, revision IDs, file paths, output, or error messages. Observers run after the task and all its subprocesses finish; thrown exceptions and rejected observer promises are ignored and never change mutation results. Async observers are not awaited; observers should be fast because synchronous observer work delays subsequent queued requests. Async-local task contexts keep concurrent display and serial subprocess records separate. Each lane retains ownership until all its task children finish, including on failure.

## Tests

`tests/squash-validation.test.ts` covers edits, operation changes, and configuration-only races during private capture, preview, conflict enumeration and final validation for both squash APIs. It also exercises malformed pre/post conflict identities and the corresponding recovery boundaries. Metadata performance tests compare bounded membership results against the original global query and retain configured alias/prefix semantics. Deterministic subprocess-budget tests guard the consolidated paths; timing assertions are reserved for local benchmarks.

`tests/recovery.test.ts` reproduces snapshots after successful attribution, snapshots during post-success validation, post-success rendering failures, and conservative session guards for snapshots before attribution, unreadable operation metadata and nonzero exits. It verifies process-local undo, restart without app bookkeeping or history changes, ignored/untouched legacy journals, disabled undo after attribution races, useful diagnostic identities, and no automatic mutation replay.

`tests/fixtures.ts` creates isolated real jj repositories solely for tests. `tests/native-selection.test.ts` verifies byte-preserving selection without subprocesses; `tests/native-diff-editor.test.ts` validates callback trees, paths, cleanup, private manifests, and real/bundled jj integration. `tests/diff.test.ts` checks native IDs and parser safety. Backend/revision tests exercise exact native selection, in-memory undo, non-@ changes, source switching, workspace and bookmark moves, abandonment/divergence, immutable/merge parents, stale and forbidden requests, graph metadata, cache isolation, failures and interleavings. Browser tests exercise the actual code/tree/graph interactions. CLI tests run the bundled executable outside the source tree and exercise loopback security, opening, validation, and foreground process-group shutdown. Nix checks run the installed package without ambient runtime tools. Editor tests use a fake runner (never the user's listening Neovim) to check literal arguments, serialized/versioned dispatch, workspace containment, errors and loopback POST protection. Performance regressions have deterministic subprocess-count tests (not wall-clock assertions). `npm run benchmark -- --runs 3 --extra-files 50` measures real temporary repositories locally.

`tests/commit-content.test.ts` exercises real immutable reads through unsnapshotted edits and hidden-commit rewrites; verifies selection/cache isolation, exact IDs and literal changed paths, root/merge/unsupported/absent sides, bounded admission/output, concurrent timing attribution, independent read/state progress, and service/HTTP shutdown draining. Existing subprocess-budget tests continue to cover unchanged state and mutation paths.

Immutable descriptor cache tests additionally cover exact warm file-read subprocess budgets, public-object mutation isolation, in-flight failure/retry, LRU entry and estimated-byte eviction, and oversized-entry bypass without demand-cache or selection changes.

Immutable read regressions create bookmarks named exactly like source/parent commit hashes and inject source-name shadowing between metadata and diff. Both cold and cached descriptors/file sides must retain the exact original commit bytes.
